项目概述

dclaw (内部代号 dwclaw) 是 Tencent dw-agent 项目的核心 CLI 运行时组件。它提供了一个可扩展的 AI Agent 框架，支持：

  • 🤖 多种 AI 模型：OpenAI 兼容 API、Claude Code、DeepSeek、通义千问、腾讯混元等
  • 📡 多渠道接入：Telegram、标准输入 (stdin)、HTTP Gateway
  • 💾 灵活存储：会话和记忆支持 In-Memory、Redis、SQLite、MySQL、PostgreSQL、ClickHouse、PGVector
  • 🧩 插件化架构：通过匿名导入轻松注入自定义通道、后端、工具和模型
  • 🛠️ 技能系统：基于 SKILL.md 的声明式技能定义和自动加载
  • 🌐 浏览器自动化：内置浏览器控制工具，支持页面交互和截图
  • ⏰ 定时任务：支持 Cron 表达式调度 AI 任务
  • 🎛️ Admin UI：内置 Web 管理界面，管理技能、会话、记忆和定时任务
  • 🔗 A2A 协议：Agent-to-Agent 通信协议支持

架构设计

设计哲学

dclaw 的架构围绕四个核心设计原则构建：

1. 插件化注册 (Plugin Registration)

所有组件通过 init() 函数向全局注册表注册，而非硬编码依赖。这使得：

  • 组件可以按需加载
  • 下游发行版可以通过匿名导入注入内部插件
  • 编译时决定可用组件，运行时动态选择
// 每个插件包在 init() 中注册自己
func init() {
    registry.RegisterChannel("telegram", newChannel)
    registry.RegisterSessionBackend("redis", newRedisSessionBackend)
    registry.RegisterToolProvider("browser", newBrowserTools)
}

2. 配置驱动 (Configuration-Driven)

所有运行时行为由配置决定，支持三层配置来源：

命令行参数 (最高优先级)
    ↓ 覆盖
YAML 配置文件
    ↓ 覆盖
环境变量 + 内置默认值 (最低优先级)

3. 分层解耦 (Layered Decoupling)

严格的分层架构，每层只依赖下一层的接口：

通道层 (Channels)    → 只依赖 GatewayClient 接口
网关层 (Gateway)     → 只依赖 Runner 接口
执行层 (Runner)      → 只依赖 Agent 接口
代理层 (Agent)       → 只依赖 Model 接口
模型层 (Model)       → 无框架依赖

4. 会话隔离 (Session Isolation)

每个用户/线程拥有完全独立的对话上下文：

  • 独立的会话存储键
  • 独立的作用域索引
  • 独立的记忆文件
  • 通过 laneLocker 保证同一会话的串行执行

核心子系统详解

1. 插件注册系统 (Registry)

路径: registry/registry.go

Registry 是 dclaw 插件化的核心枢纽。它提供了六种注册表，每种管理一类组件：

var (
    channelFactories  = map[string]ChannelFactory{}       // 通道
    sessionFactories  = map[string]SessionBackendFactory{} // 会话后端
    memoryFactories   = map[string]MemoryBackendFactory{}  // 记忆后端
    toolFactories     = map[string]ToolProviderFactory{}   // 工具提供者
    toolSetFactories  = map[string]ToolSetProviderFactory{}// 工具集提供者
    modelFactories    = map[string]ModelFactory{}          // 模型
)

注册流程 

插件包 init()
    │
    ▼
registry.RegisterChannel("telegram", newChannel)
    │
    ▼
检查名称有效性 → 检查是否重复 → 存入 map
    │
    ▼
运行时通过 registry.LookupChannel("telegram") 获取工厂

工厂函数签名

每种组件类型有特定的工厂函数签名：

// 通道工厂：接收依赖和配置，返回 Channel 实例
type ChannelFactory func(
    deps ChannelDeps,      // Gateway 客户端、状态目录、上下文
    spec PluginSpec,       // 类型、名称、YAML 配置节点
) (channel.Channel, error)

// 会话后端工厂
type SessionBackendFactory func(
    deps SessionDeps,      // Model、Summarizer、AppName
    spec SessionBackendSpec,
) (session.Service, error)

// 记忆后端工厂
type MemoryBackendFactory func(
    deps MemoryDeps,       // Model、Extractor、AppName
    spec MemoryBackendSpec,
) (memory.Service, error)

// 工具提供者工厂：返回静态工具列表
type ToolProviderFactory func(
    deps ToolProviderDeps,
    spec PluginSpec,
) ([]tool.Tool, error)

// 工具集提供者工厂：返回动态工具集合
type ToolSetProviderFactory func(
    deps ToolSetProviderDeps,
    spec PluginSpec,
) (tool.ToolSet, error)

// 模型工厂
type ModelFactory func(spec ModelSpec) (model.Model, error)

关键设计模式

并发控制：Lane Locker

问题：同一用户的多个并发请求可能导致对话状态混乱。

解决方案：laneLocker 按 sessionID 进行会话级互斥。

type laneLocker struct {
    mu    sync.Mutex
    lanes map[string]*laneEntry  // sessionID → laneEntry
}

func (l *laneLocker) withLock(key string, fn func()) {
    entry := l.acquire(key)    // 获取或创建 lane
    entry.lock.Lock()           // 会话级互斥
    defer func() {
        entry.lock.Unlock()
        l.release(key, entry)   // 引用计数减少，清理空闲 lane
    }()
    fn()                        // 在锁内执行
}

设计亮点：

  • 引用计数：多个 goroutine 可以等待同一 lane，避免创建多余的锁
  • 自动清理：引用计数归零时自动移除 lane 条目，防止内存泄漏
  • 非阻塞获取：不同 sessionID 的请求完全并行，互不影响
Request A (session: "telegram:dm:123")  → acquire("telegram:dm:123") → 获得锁 → 执行
Request B (session: "telegram:dm:123")  → acquire("telegram:dm:123") → 等待锁
Request C (session: "telegram:dm:456")  → acquire("telegram:dm:456") → 获得锁 → 执行 (并行)

取消追踪：Cancel Tracker

问题：用户可能取消正在执行的请求，需要通知 Runner 停止。

解决方案：cancelTracker 维护已取消的 requestID 集合。

type cancelTracker struct {
    mu  sync.Mutex
    ids map[string]struct{}
}

func (t *cancelTracker) Mark(requestID string)   // 标记为已取消
func (t *cancelTracker) Take(requestID string) bool  // 检查并移除

流程：

POST /cancel {"request_id": "uuid-xxx"}
    │
    ▼

    │
    ▼
Runner 执行过程中定期检查
    │
    ▼
cancelTracker.Take("uuid-xxx") → true → 停止执行

上下文注入：RunOption Resolver

问题：不同组件需要向 Runner 注入不同的运行时上下文。

解决方案：RunOptionResolver 链式注入。

type RunOptionResolver func(
    ctx context.Context,
    input RunOptionInput,
) (context.Context, []agent.RunOption)

注册链：

Gateway
    │
    ├── Langfuse Resolver      → 注入追踪上下文
    ├── Delivery Resolver      → 注入投递上下文
    ├── Conversation Resolver  → 注入对话历史
    └── 自定义 Resolver        → 下游发行版注入
    │
    ▼
合并所有 RunOption → 传递给 Runner

设计亮点：

  • 每个 Resolver 独立、可组合
  • 可以修改 context 和添加 RunOption
  • 支持下游发行版注入自定义逻辑

流式聚合：Reply Accumulator

问题：Runner 返回的是事件流，需要聚合为最终回复。

解决方案：replyAccumulator 消费事件流并聚合。

type replyAccumulator struct {
    Text      string       // 聚合的回复文本
    RequestID string       // 请求 ID
    Error     error        // 捕获的错误
    Usage     *Usage       // Token 用量

    seenFull bool          // 是否已收到完整回复
    builder  strings.Builder  // 增量文本构建器
}

func (a *replyAccumulator) Consume(evt *event.Event) {
    switch evt.Object {
    case model.ObjectTypeChatCompletion:
        a.consumeFull(evt.Response)    // 完整回复
    case model.ObjectTypeChatCompletionChunk:
        a.consumeDelta(evt.Response)   // 增量片段
    }
    a.captureUsage(evt.Response)       // 累积 Token 用量
}

聚合逻辑：

事件流:
    Chunk 1: "你"
    Chunk 2: "好"
    Chunk 3: "！"
    Done: true
    │
    ▼
replyAccumulator:
    builder.WriteString("你")
    builder.WriteString("好")
    builder.WriteString("！")
    │
    ▼
Text = "你好！"
Usage = {PromptTokens: 10, CompletionTokens: 3, TotalTokens: 13}

快速开始

环境要求

  • Go 1.21+（推荐 Go 1.22+）
  • 操作系统：Linux、macOS、Windows
  • 可选依赖：
    • CGO：用于 SQLite 后端（如果不需要 SQLite，可设置 CGO_ENABLED=0）
    • Redis：用于 Redis 后端
    • MySQL / PostgreSQL / ClickHouse：用于对应后端

编译 

git clone <repository-url>
cd dclaw

# 编译默认二进制（包含 stdin + telegram 通道）
go build -o dclaw ./cmd/dclaw/

# 不带 CGO 编译（禁用 SQLite 后端）
CGO_ENABLED=0 go build -o dclaw ./cmd/dclaw/

最小化运行（stdin 交互模式） 

./dclaw run \
  --model-mode openai \
  --openai-model gpt-4o \
  --openai-base-url https://api.openai.com/v1 \
  --channels stdin

# 环境变量方式
export OPENAI_BASE_URL=https://api.openai.com/v1
export OPENAI_MODEL=gpt-4o
./dclaw run --channels stdin

Gateway API

端点

端点 方法 描述
GET /healthz GET 健康检查
POST /v1/gateway/messages POST 发送消息
POST /v1/gateway/messages/stream POST SSE 流式响应
GET /v1/gateway/status?request_id=... GET 查询状态
POST /v1/gateway/cancel POST 取消请求

发送消息 

curl -X POST http://localhost:8080/v1/gateway/messages \
  -H "Content-Type: application/json" \
  -d '{"channel":"http","from":"user1","text":"你好","thread":"default"}'

响应：

{
  "request_id": "uuid-xxx",
  "session_id": "http:dm:user1",
  "reply": "你好！有什么可以帮助你的？",
  "usage": {"prompt_tokens": 10, "completion_tokens": 15, "total_tokens": 25}
}

curl -X POST http://localhost:8080/v1/gateway/messages/stream \
